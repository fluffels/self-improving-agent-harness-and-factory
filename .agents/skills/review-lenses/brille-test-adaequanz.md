**Lens 3 — Test-Adäquanz.** Deckt der Test das **Verhalten** ab — und ist er echt?

Regel-Ausschnitt: TDD und Red-Green. Mehr aus der Root-Kontextdatei liest du nicht.

- Prüft der Test die **öffentliche API / beobachtbares Verhalten** (überlebt Refactoring), nicht Interna?
- **Plan-Prüfliste (Plan-Abschnitt 4):** Ein geplanter Negativfall ohne Test oder eine anders entschiedene Weiche ohne Begründung in Commit oder PR ist ein Blocker.
- **Negativfälle** dabei (kaputter Zustand, falsche Eingabe, „darf nicht passieren"), nicht nur Happy Path? Bei Generatoren jede Kantenart und jeden Sortierschlüssel per Fixture abdecken, Substring-Asserts am Zeilenanfang verankern (`ext_q_a` enthält `q_a`). Hat jede neue Bedingung (Filter, Guard, Sonderfall, catch/Weiterwurf) einen Test, der genau diesen Zweig auslöst? Ein Sammel-`n.a.` über eine Anker-Art („catch-Zweige n.a.“) ist ein Fund. Liest ein Test über eine Standard-Wurzel (Repo des Skripts) ungetrackten oder gitignorierten Zustand des Checkouts (`.codex/`, `.claude/worktrees`, Temp)? Dann Fixture-Wurzel übergeben. Räumen Tests Temp-Ordner und -Dateien auf (afterEach/finally), und schreibt kein Test ins Repo?
- **Sweep-Tiefe (factory#272, die eine Stelle der Staffel):** hole `node scripts/groessenstufe.mjs` im selben Shell-Aufruf wie `node scripts/anker-liste.mjs` und lies die Zeile `SWEEP:`. `voll` oder fehlende Zeile: der Vollsweep des nächsten Punkts. `stichprobe` (nur Doku und Testdateien, Risikoklasse nicht hoch): **Stichprobenregel Text-Wächter**, je geänderter Testdatei höchstens 3 Sabotage-Proben (erste und letzte neue oder geänderte Assertion, dazu ein Negativfall, falls vorhanden), sabotiert wird die geprüfte Stelle; bleibt eine Probe grün, ist das ein Fund und die ganze Datei bekommt in derselben Runde den Vollsweep. Alle anderen Prüfpunkte gelten unverändert.
- **Guards vollständig, keine Stichprobe (Runde 1, bei `SWEEP: voll`):** Grundlage: `node scripts/anker-liste.mjs` im Lens-Worktree (Anker je geänderter Funktion in Code-Dateien außer Tests, auch `test/support`, ohne AST) plus Guards außerhalb ihrer Musterliste (`?.`, `??`, `if (!x) return`, Default-Parameter, mehrzeilige Ausdrücke, je Regex- oder Fenster-Parameter beide Grenzen; dazu die Verdrahtung reiner Helfer an der Aufrufstelle, `opt: helfer(…)`: ein Test muss rot werden, wenn das Argument fehlt); je Anker den Test nennen, den eine Sabotage rot macht; ein Anker ohne solchen Test ist ein Fund der ersten Runde. Je Regex jede Komponente (Anker, Klasse, Quantor, Alternative, Gruppe) beidseitig, schon in Runde 1: der Umsetzer protokolliert den Vollsweep als `<datei> | <Suchstring> → <Ersatz> | <Test> | Ergebnis`, die Test-Lens fährt Proben daraus nach (Commit-Bodys, `git log origin/main..HEAD --format=%B`; der Spawn nennt die Commits im Kopf-Feld `Probe-Protokoll:`, „keins“ ist ein Fund), bei Zweifel alle. Vorschläge vorher am realen Verhalten prüfen (Aufruf, Fixture).
- **Kein False Positive (Red-Green):** würde der Test **rot**, wenn man die Logik testweise verfälscht? Wo Zweifel bestehen, den Fix/die Assertion kurz sabotieren (per Edit-Tool, nicht `sed`: unter Git-Bash greift ein Backslash-Ausdruck still nicht; vor dem Testlauf muss `git -C <lens-worktree> diff --stat` die Datei zeigen, sonst ungültig; Probe-Skripte zählen den Anker vorher und brechen bei ≠ 1 Treffer ab) → rot sehen; die Probe fährt alle Tests, die den verfälschten Code abdecken (Importeure per `grep -rl <modul> test/`), nicht nur eine Datei, und Rot in anderer Datei heißt abgedeckt, kein Fund → zurücksetzen (vgl. AGENTS.md „Tests gegen False Positives absichern"). Blockt der Auto-Mode die Probe: Probe an einer Scratchpad-Kopie der Prüffunktion, sonst „Sabotage-Probe nicht durchführbar (Auto-Mode)“ melden, nie als bestanden. Bugfix ⇒ gab es den **fehlschlagenden Repro-Test zuerst**?
- **Git-Proben als Vitest-Fixture:** ein Wegwerf-Repo baut der Test mit `execFileSync("git", …, { cwd: tmp })` im Temp-Ordner (Muster `test/merge-testabgleich.test.ts`, `aufbau`), kein `git -C <Scratchpad-Repo>` aus der Shell.
- **Echte Gate-Sabotage bei abgeleiteten Regeln:** leitet der Diff Gate-Regeln aus einem Modell ab (z.B. die Schichtregeln von `check:arch` aus `SCHICHT_MODELL`), verlangt die Lens einen Test, der das **echte Gate** laufen lässt (verbotene Kante in eine Temp-Fixture einschleusen, das Gate muss rot werden, eine erlaubte Kante grün bleiben). Ein Nachbau des Matchers im Test genügt nicht: er beweist nur, dass die Ableitung richtig rechnet, nicht, dass das Gate sie anwendet.
- **Sperre gegen die Diff-Basis:** vergleicht ein Test den Stand mit der Diff-Basis (Baseline darf nicht steigen, Liste nicht schrumpfen), muss die Erlaubnis eine **Ableitungsfunktion** sein (Vorbild `erlaubteWerte`: aus Alt- und Neustand die erlaubten Werte berechnen), und die Funktion hat einen eigenen **Mechanik-Test** (Fixtures für erlaubt, verboten, fehlende Basis). Eine im Test inline gerechnete Erlaubnis ohne Mechanik-Test ist ein Fund.
- **Differenztest:** er ist nur so stark wie jede Fixture, die ihren Guard auslöst; jede Fixture per Sabotage ihres Guards prüfen. Ein Scan-Wächter gilt erst als belegt, wenn ein eingeschleuster bekannter Fund ihn rot macht; `String.fromCharCode(92, 92)` ergibt zwei Backslashes, die Regex trifft dann ein wörtliches `\` (Probe: `new RegExp(String.fromCharCode(92,92)+"d")` hat Quelle `\\d`).
- **Vertrauens- und Ausblendungsverhalten** mit `toBe` auf den ganzen Titel prüfen, kein bloßes `toContain`.
- **Orakel-Test:** prüft ein Test eine Liste gegen ein Orakel, braucht **jede** Liste eine **unabhängig aus der Quelle abgeschriebene Gegenliste**, auch die Einträge, die eine Hilfsfunktion erzeugt (eine aus dem Code gerechnete Gegenliste beweist nur, dass der Code sich selbst gleicht). „Einmal hinterlegt“ heißt zusätzlich: keine Wiederholung zwischen Ebenen (Test, Skript, Doku), sonst driftet eine Kopie.
- **Wächter und Default-Parameter (factory#208):** Prüft ein Wächter-Test eine Verwendung nur per `includes("<name>")`, erfüllt ihn ein Import oder Kommentar: auf `name(` prüfen. Ein Default-Parameter, den nur der Produktionsweg nutzt, braucht einen Test mit abweichend eingespritztem Wert, sonst ist die Konstante gleich dem Wert im Quellrepo und der Test vakuös.
- Präsentations-Code (UI-Framework/DOM) wird **im Browser** verifiziert statt per Unit-Test, ebenso sicht- oder bedienbare Content-Daten (Quests, Dialoge) — ist das passiert und belegt, wie im Plan vorgesehen (Zustands-Auszug des Dev-Helfers, Screenshot-Pfad)?

**Escape-Hinweis zum Write-Tool:** Das Write-Tool dekodiert `\uXXXX`: Escapes per `String.fromCharCode(92)` bauen, danach auf Nicht-ASCII prüfen, Anker mit Backslash per Write ablegen und als `String.raw` schreiben; ein Probe-Skript mit Regex gehört nicht in einen Bash-Heredoc `<<'EOF'` (er halbiert Backslashes, die Anker zählen still 0): per Write ins Scratchpad schreiben, die Trefferzahl vorher ausgeben.

> **Was die Kontext-Diät ausdrücklich NICHT trifft:** die **Sabotage-/Red-Green-Prüfung** der Test-Lens (Implementierung testweise verfälschen → wird ein Test rot?). Sie ist der teuerste Schritt und der einzige, der harte Fehler statt Stil-Anmerkungen liefert — in der Messsession fand genau sie den einzigen echten Blocker. Sie bleibt bei `SWEEP: voll` vollständig, bei `SWEEP: stichprobe` nach der Stichprobenregel; sie ist auch die eine erlaubte Ausnahme von „die Lens ändert nichts" (in einem eigenen Lens-Worktree, nie im Feature-Worktree).

# Fortschreibung #182 (2026-11-04): Gate-Befehle aus der Projekt-Config

Ergänzt [ADR 0022](../0022-dark-factory-kern-und-verteilung.md) (Projektwerte zur Laufzeit aus der Projekt-Config, Kern ohne Projektliteral); die Fortschreibung steht als Datei (siehe [Fortschreibung zu ADR 0013](0013-1860-fortschreibungen-als-dateien.md)). Sie ist Teil von factory#171 (Java-Profil): ein Projekt ohne npm als Build-Werkzeug setzt seine Sammelbefehle selbst.

- **Entscheidung (Läufer statt Platzhalter):** ein Block `befehle` der Projekt-Config mit der geschlossenen Namensliste `install`, `verify`, `verifyKompakt`, `verifyChanged`, `coverage` und der Läufer `node scripts/gate-befehl.mjs <name>`. Ein Aufruf gilt für Claude, Codex, pre-push und CI, die Kern-Texte bleiben projektneutral. Keine Platzhalter-Gruppe in der Projektwerte-Tabelle: sie hätte jede Kern-Prosa mit dem Befehl vollgeschrieben und bei jedem Wechsel neu erzeugt werden müssen.
- **Entscheidung (Standard):** ohne Block, und für jeden Namen ohne Eintrag, gelten `npm ci`, `npm run verify`, `npm run verify:kompakt`, `npm run verify:changed`, `npm run test:coverage`. Ein Teil-Block ist erlaubt (`befehle.verify` allein); ein vergessener Name scheitert laut (npm ohne Skript), nicht still grün.
- **Entscheidung (Ausführung):** die Befehlszeile läuft als String mit `shell: true` (unter Windows scheitert `npm.cmd` sonst), im Wurzelordner des Läufers statt in `process.cwd()` (pre-push, CI und Agenten rufen aus verschiedenen Ordnern), mit `stdio: inherit`. Signal oder Startfehler ergeben Exit 1 (fail-closed). Ein Zeilenumbruch im Wert ist ein Formfehler, weil cmd.exe nur die erste Zeile ausführt.
- **Entscheidung (Form):** unbekannter Name oder kaputte Form ergibt Exit 2 mit Fix-Zeile, bevor die Config geladen wird (Namensprüfung per `Object.hasOwn`, nie `in`: `constructor` ist kein Name). Lib und Einstieg sind zwei Kern-Dateien, weil die Config-Lib die Formprüfung ohne Import-Zyklus braucht; der Lader wird in die Lib injiziert.
- **Entscheidung (Verdrahtung):** `.githooks/pre-push` (Kern) und der Verify-, Coverage- und Installationsschritt der `ci.yml` (Projektbesitz, dieses Repo) rufen den Läufer; `check:diffcoverage` bleibt ein eigener Schritt, der Job-Name des Required-Checks bleibt. Die Wurzel-`package.json` bleibt Task-Runner des Harness: Harness-Gates, `docs-gen` und `verify-lauf` setzen npm-Skripte voraus.
- **Bekannte Grenzen:** endet der Befehl selbst mit 2, ist das vom Aufruf-Fehler nur an der Fix-Zeile auf stderr zu unterscheiden (pre-push und CI werten nur „ungleich 0“). Die Kern-Texte von Skills und Agenten beider Laufzeiten nennen noch `npm run verify:kompakt`; sie stellt factory#186 um. `.github/workflows/verify-macos.yml` (Projektbesitz) ruft noch die npm-Befehle und läuft manuell.
- **Re-Evaluierung:** wenn ein Bezieher ein Build-Werkzeug mit mehrzeiligem Gate-Ablauf nutzt (dann ein Skript statt einer Zeile) oder wenn factory#186 die Kern-Texte umgestellt hat.

# Fortschreibung #116 (2026-10-30): Harness-Doctor prüft acht Sicherheitspunkte

Ergänzt [ADR 0022](../0022-dark-factory-kern-und-verteilung.md) (Harness-Doctor, Fortschreibung #1800); die Fortschreibung steht als Datei (siehe [Fortschreibung zu ADR 0013](0013-1860-fortschreibungen-als-dateien.md)).

- **Ausgangslage:** der Doctor prüfte Actions, Secrets, Labels, Boards und das Ruleset, aber keine der Einstellungen, die ein Repo gegen Geheimnis-Lecks und Lieferketten-Angriffe härten. Ein Endpunkt, der ohne Admin-Recht nichts liefert, wäre als „kein Befund“ still grün geworden.
- **Entscheidung (acht Punkte, drei Ausgänge):** `Secret Scanning`, `Push Protection`, `Non-Provider-Patterns`, `Validity Checks`, `PVR`, `Dependabot Security Updates`, `Code-Scanning` und `SHA-Pinning` erscheinen in `--pruefen` immer als eigene Zeile: `OK`, `LÜCKE` (belegt ausgeschaltet) oder `NICHT PRÜFBAR <Punkt>: <Grund> Fix: …` (nicht belegbar). Exit 1 ab einer Lücke oder einem nicht prüfbaren Punkt; die Summenzeile zählt beide getrennt.
- **Entscheidung („nicht prüfbar“ ist kein Fehlerzustand der Prüfung):** ein Endpunkt-Fehler (403, 404, Netzfehler) und ein fehlendes oder unbekanntes Feld (`security_and_analysis` ohne Admin-Recht, `sha_pinning_required`, PVR) ergeben „nicht prüfbar“ mit dem Grund, nie OK und nie eine behauptete Lücke. Das Ergebnis trägt `ok: false` und `nichtPruefbar: true`; so bleiben alle Verbraucher (`!p.ok`, `--einrichten`, Wochenlauf) ohne Änderung richtig.
- **Entscheidung (Quellen):** fünf Punkte aus `security_and_analysis` der Repo-Antwort (Dependabot Security Updates dort statt aus `automated-security-fixes`, weil dessen 404 „aus“ bedeutet und sich nicht von einem Fehler unterscheiden lässt), PVR aus `private-vulnerability-reporting`, SHA-Pinning aus `actions/permissions`, Code-Scanning aus den Branch-Regeln gegen `codeScanning` des Ruleset-Spiegels (die Prüfung zog aus dem Punkt `Ruleset` hierher, damit jeder Punkt genau eine Zeile hat; ohne Werkzeug im Spiegel genügt ein live vorhandenes, sonst ist es eine Lücke). Die Prüflogik ist pur (`scripts/harness-doctor-sicherheit.mjs`), die Lib liest die Quellen je einmal.
- **Entscheidung (`--einrichten` ändert nichts):** die acht Punkte sind nur `ANLEITUNG … Link: …`; der Fix-Text ist ein Klickpfad in den Einstellungen, kein `gh api -X PATCH`. Ein Test belegt, dass dabei kein schreibender `gh`-Aufruf entsteht (erlaubt bleibt der Label-POST).
- **Entscheidung (Wochenlauf):** Lücken und nicht prüfbare Punkte werden Zeilen im Sammelticket; der Abgleich gegen offene Zeilen bleibt, der Schlüssel trägt jetzt die Art (`LÜCKE <Punkt>: ` oder `NICHT PRÜFBAR <Punkt>: `), weil sich die Abhilfe ändert, wenn aus „nicht prüfbar“ eine Lücke wird. Der Schlüssel der Lücke ist unverändert.
- **Bekannte Grenzen:** die Zeile `LÜCKE Code-Scanning <Werkzeug>:` heißt jetzt `LÜCKE Code-Scanning:` (alle fehlenden Werkzeuge in einer Zeile); ein Bezieher mit offener alter Zeile bekommt einmalig eine neue. Der Schlüssel `secret_scanning_validity_checks` steht nicht in der REST-Doku von „Get a repository“, die Live-Probe mit Admin-Recht (2026-10-30) zeigt ihn aber; fehlt er in einem Projekt, bleibt der Punkt nicht prüfbar. Wo dem Plan eines Projekts eine Funktion fehlt, kommt der Doctor dauerhaft nicht auf Exit 0 (gewollt, nie still grün; der Wochenlauf meldet die Zeile dank Abgleich einmal). Die bestehenden Punkte (Actions, Secrets, Labels, Board, Ruleset, Admin-Recht) melden einen unlesbaren Endpunkt weiter als Lücke.
- **Re-Evaluierung:** wenn GitHub die REST-Antwort um weitere Sicherheitseinstellungen erweitert oder die bestehenden Punkte auf den dritten Ausgang umgestellt werden.

# Fortschreibung #89 (2026-11-06): Aufräumen und Guards arbeiten im Arbeitsplatz je Repo der Config

Ergänzt [ADR 0022](../0022-dark-factory-kern-und-verteilung.md) (Betriebsart Arbeitsplatz, factory#87, factory#88); die Fortschreibung steht als Datei (siehe [Fortschreibung zu ADR 0013](0013-1860-fortschreibungen-als-dateien.md)).

- **Entscheidung (je Repo der Config, ein Lauf über alle):** Der Stop-Hook (`checkAndFixOrphanWorktrees`) und `cleanup-worktrees` räumen im Arbeitsplatz je Repo des Blocks `arbeitsplatz` auf (`aufraeumDiagnose` in `scripts/worktree-aufraeumen.mjs`: ein Befund je Repo, Worktree-Ordner `<wurzel>/.claude/worktrees/<name>`). Beide räumen in einem Lauf alle Repos ab; die CLI trennt die Ausgabe je Repo mit dem Kopf `=== Repo <name> (<worktree-ordner>) ===` und gibt das Maximum der Repo-Exit-Codes zurück, `--branches` ruft die Branch-Aufräumung je Repo (git im Repo, `gh` mit dessen Arbeitsverzeichnis). Eingebettet (ohne Block) bleibt das Verhalten zeichen- und aufrufgleich. Registrierte Feature-Worktrees entfernt das Aufräumen weiter nie; das bleibt Sache von `claims-pruefen` und des Umsetzers.
- **Der Gurt erwartet den Ordner aus der Config:** `assertSafeOrphanTarget` löscht nur ein echtes Verzeichnis unterhalb des `worktreeOrdner` des Repos, dessen `pfad` der `mainRoot` ist (`erwarteterWorktreeOrdner`; unter Windows ohne Beachtung der Groß-/Kleinschreibung). Ein `mainRoot` ohne Repo der Config, ein falscher Ordner (etwa `<wurzel>/.claude/worktrees`, in dem die Repo-Ordner liegen) und ein Worktree-Ordner, der selbst ein Link ist, lehnt der Gurt ab. Der Ordner mit den Repo-Ordnern wird nie gescannt: ohne diese Regel hätte ein Arbeitsplatz, dessen Basis ein Git-Repo ist, die Repo-Ordner als Waisen gelöscht (dieselbe Klasse wie quellprojekt#1051).
- **Vereinigung der registrierten Pfade, fail-closed über alle Repos:** Ordner- und Datei-Waisen eines Repos gelten gegen die Vereinigung der `git worktree list`-Pfade aller Repos; ein aktiver Worktree von Repo B im Ordner von Repo A wird nie gelöscht. Lens-Waisen prüft das Aufräumen nur gegen die Liste des eigenen Repos. Scheitert `git worktree list` in einem Repo oder liefert es nichts, wird in keinem Repo etwas gelöscht: der Stop-Hook meldet eine Warnung (`systemMessage`, keine Blockade), die CLI Exit 1 mit Repo-Name und `Fix:`-Zeile. Ein kaputter Block `arbeitsplatz` blockiert den Stop mit der Fix-Zeile (wie eine fehlende Config, quellprojekt#1742). Ordner unter `<wurzel>/.claude/worktrees` ohne Repo der Config meldet nur die CLI, gelöscht werden sie nie. Der Datenverlust-Alarm (versionierte Dateien unter `.claude/`) läuft im Arbeitsplatz in der Wurzel und bleibt bei einem git-Fehler fail-open.
- **Worktree-Guard schützt jedes Repo der Config:** `schutzWurzeln` liefert das Session-Repo und im Arbeitsplatz jedes Repo des Blocks; `decide` (Bash) und `bewertePowerShell` bewerten je Wurzel (ein Block geht vor einer Rückfrage, diese vor dem Durchlassen, `jeSchutzWurzel`). Ein Commit oder Push im Haupt-Checkout von `web` oder `api` blockt darum auch, wenn das Arbeitsverzeichnis die Arbeitsplatz-Wurzel ist (kein Git-Repo); ein Linked Worktree unter `<wurzel>/.claude/worktrees/<name>/` geht durch. Der Hinweistext nennt den Befehl aus `arbeitsplatz.mjs worktree` (`worktreeBefehl`, Basis `origin/<standardzweig>` des getroffenen Repos); eingebettet bleibt der Text zeichengleich. Ist der Block kaputt oder die Config nicht lesbar, bleibt es beim Session-Repo: ein Totalblock würde auch Commits im Worktree verhindern.
- **Lens-Edit-Guard:** Das Muster nahm das Repo-Segment `<repo>/` schon auf (factory#87); der Hinweis nennt im Arbeitsplatz `<worktree-ordner>/<praefixe.worktree><nr>-lens-r<runde>` und `node scripts/arbeitsplatz.mjs pfade`. `lens-auftrag-guard` bleibt unverändert (`origin/main` steht dort nur in einem Kommentarbeispiel).
- **T6, Messwerkzeuge:** `mcp-ausfall` kürzt einen Worktree unter `.claude/worktrees/<repo>/<name>` auf die Arbeitsplatz-Wurzel (`hauptWurzel(…, mitArbeitsplatz)`, nur mit Block in der Config; ohne ihn bleibt der Pfad unverändert, weil `<repo>/<name>` sonst nicht von einem tieferen Pfad zu unterscheiden ist). `transkript.projektOrdner` nimmt im Arbeitsplatz den Slug der Basis (Ordner mit `.factory/projekt.json`) statt des Hauptrepos per git; `hauptrepoPfad` und `projektSlug` kürzten schon beim ersten `.claude/worktrees`.
- **Grenze Codex:** Die Hooks (Stop, PreToolUse) gelten in Codex nicht automatisch ([Codex](../../codex/einstieg.md)); der Umsetzer-Text (Schritt 6) ist auch die Codex-Quelle und nennt den Worktree-Ordner je Repo. Eine Hook-Registrierung ändert dieser Schritt nicht, darum entfällt der Langfuse-Probe-Lauf.

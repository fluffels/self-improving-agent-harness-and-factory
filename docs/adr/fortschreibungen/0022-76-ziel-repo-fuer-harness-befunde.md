# Fortschreibung #76 (2026-10-27): Ziel-Repo für Harness-Befunde

Ergänzt [ADR 0022](../0022-dark-factory-kern-und-verteilung.md) (F10, Teil 11); die Fortschreibung steht als Datei (siehe [Fortschreibung zu ADR 0013](0013-1860-fortschreibungen-als-dateien.md)). Setzt auf der Board-Zuordnung `boards[].repo` auf, die ein Board an ein Repo bindet.

- **Das Ziel-Repo ist das Repo des Factory-Boards:** `zielRepoFuer(labels, config)` (`scripts/projekt-config-lib.mjs`) liefert zur Board-Rolle der Labels (`boardRolleFuer`, hierher gezogen, `board-lib` exportiert sie weiter) das Repo, dessen Issues das Board führt (`boards[].repo`, ohne Schlüssel das eigene `repo`). Ein neuer Schlüssel entfällt: ohne `boards[factory].repo` bleibt alles im eigenen Repo. Die CLI `node scripts/projekt-config.mjs --ziel-repo <label>` gibt es aus (Shell, Workflows, Doku-Snippets).
- **Schreibwege landen im Ziel-Repo oder brechen klar ab:** `loadItems(board, { repo })` filtert zentral auf die Items des Repos (`nurRepo`; `repo` ist Pflicht), `addToBoardTodo` wirft vor jedem `gh`-Aufruf bei einem Board, das ein anderes Repo führt. `aufnahmePlan` lehnt ein fremd geführtes Issue mit Grund ab, `umzugsPlan` meldet es, `board-place --repo <owner/name>` wählt das Repo der Nummern und bricht (Exit 2) bei einem Board ab, das ein anderes führt. `spezifikation anlegen` und `sammelticket-anlegen` legen im Ziel-Repo an (`inbox-lib` liest dort Sammelticket und Kommentare und liefert dessen Owner als Vertrauensgrenze).
- **Fehlende Schreibrechte sind eine Meldung:** `schreibrechtText` (`scripts/gh-cli.mjs`) erkennt `HTTP 403/404`, „Resource not accessible by integration“ und „Must have admin rights“; ein öffentliches Repo legt das Issue für Nicht-Mitarbeiter an und verwirft die Labels still, das erkennt `fehlendeLabels` an der Antwort (Exit 2 mit Nummer und Fix). Nie ein Rückfall ins eigene Repo.
- **Board-Takt:** führt das Factory-Board ein anderes Repo als das laufende, entfallen Status-Ticket, Harness-Sammelticket und Quotenzeile (der Takt im Ziel-Repo pflegt sie), der Board-Wächter läuft weiter und lehnt Harness-Issues des eigenen Repos mit Warnung ab.
- **Dependabot-Inbox:** die Vorprüfung vor dem Anlegen bricht ab, wenn `labels.dependabotInbox` zu einem fremd geführten Board gehört (Fix: ein Label des eigenen Boards).
- **Entscheidung (Pflichtparameter `repo` statt Standardwert):** ein vergessenes `repo` würde die Items zweier Repos auf einem Board vermischen, eine Nummer träfe das falsche Issue; fail-closed wirft es. Board-Repos rechnen immer aus der Config, nie aus `GITHUB_REPOSITORY` (sonst kippt die Fremd-Config-Probe).
- **Bekannte Grenze:** Inbox-Wege mit Harness-Standardlabel (`wiedervorlage`, Alarm-Inboxen) legen im eigenen Repo an und brechen dann am Guard von `board-place` ab; die Zählung der Produktquote läuft im Takt nur über das eigene Repo. Beides ist als Befund im Sammelticket notiert.
- **Re-Evaluierung:** wenn ein zweites Projekt dasselbe Factory-Repo nutzt (Kommentar-Füllstand und Quote über mehrere Repos) oder die Schreibrechte per App statt Token laufen.

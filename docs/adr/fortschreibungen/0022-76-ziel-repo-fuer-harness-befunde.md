# Fortschreibung #76 (2026-10-27): Ziel-Repo für Harness-Befunde

Ergänzt [ADR 0022](../0022-dark-factory-kern-und-verteilung.md) (F10, Teil 11); die Fortschreibung steht als Datei (siehe [Fortschreibung zu ADR 0013](0013-1860-fortschreibungen-als-dateien.md)). Setzt auf der Board-Zuordnung `boards[].repo` auf, die ein Board an ein Repo bindet.

- **Das Ziel-Repo ist das Repo des Factory-Boards:** `zielRepoFuer(labels, config)` (`scripts/projekt-config-lib.mjs`) liefert zur Board-Rolle der Labels (`boardRolleFuer`, hierher gezogen, `board-lib` exportiert sie weiter) das Repo, dessen Issues das Board führt (`boards[].repo`, ohne Schlüssel das eigene `repo`). Ein neuer Schlüssel entfällt: ohne `boards[factory].repo` bleibt alles im eigenen Repo. Die CLI `node scripts/projekt-config.mjs --ziel-repo <label>` gibt es aus (Shell, Workflows, Doku-Snippets).
- **Schreibwege landen im Ziel-Repo oder brechen klar ab:** `loadItems(board, { repo })` filtert zentral auf die Items des Repos (`nurRepo`; `repo` ist Pflicht), `addToBoardTodo` wirft vor jedem `gh`-Aufruf bei einem Board, das ein anderes Repo führt. `aufnahmePlan` lehnt ein fremd geführtes Issue mit Grund ab, `umzugsPlan` meldet es, `board-place --repo <owner/name>` wählt das Repo der Nummern und bricht (Exit 2) bei einem Board ab, das ein anderes führt. `spezifikation anlegen` und `sammelticket-anlegen` legen im Ziel-Repo an (`inbox-lib` liest dort Sammelticket und Kommentare und liefert dessen Owner als Vertrauensgrenze).
- **Fehlende Schreibrechte sind eine Meldung:** `schreibrechtText` (`scripts/gh-cli.mjs`) erkennt `HTTP 403/404`, „Resource not accessible by integration“ und „Must have admin rights“; ein öffentliches Repo legt das Issue für Nicht-Mitarbeiter an und verwirft die Labels still, das erkennt `fehlendeLabels` an der Antwort (Exit 2 mit Nummer und Fix). Nie ein Rückfall ins eigene Repo.
- **Board-Takt:** führt das Factory-Board ein anderes Repo als das laufende, entfallen Status-Ticket, Harness-Sammelticket und Quotenzeile (der Takt im Ziel-Repo pflegt sie), der Board-Wächter läuft weiter und lehnt Harness-Issues des eigenen Repos mit Warnung ab.
- **Dependabot-Inbox:** die Vorprüfung vor dem Anlegen bricht ab, wenn `labels.dependabotInbox` zu einem fremd geführten Board gehört (Fix: ein Label des eigenen Boards).
- **Entscheidung (Pflichtparameter `repo` statt Standardwert):** ein vergessenes `repo` würde die Items zweier Repos auf einem Board vermischen, eine Nummer träfe das falsche Issue; fail-closed wirft es. Board-Repos rechnen immer aus der Config, nie aus `GITHUB_REPOSITORY` (sonst kippt die Fremd-Config-Probe).
- **Bekannte Grenze:** Inbox-Wege mit Harness-Standardlabel (`wiedervorlage`, Alarm-Inboxen) legen im eigenen Repo an und brechen dann am Guard von `board-place` ab; die Zählung der Produktquote läuft im Takt nur über das eigene Repo. Beides ist als Befund im Sammelticket notiert.
- **Re-Evaluierung:** wenn ein zweites Projekt dasselbe Factory-Repo nutzt (Kommentar-Füllstand und Quote über mehrere Repos) oder die Schreibrechte per App statt Token laufen.

## Nachtrag factory#153: Meldestelle je Bezieher

- **Entscheidung (eigener Schlüssel `meldestelle`):** ein String `owner/name` in der Projekt-Config, Standard das Repo des Boards mit Rolle `factory`; das Sammelticket dort wird per Titel gewählt. Kein Objekt, weil Repo und Titel die einzigen Angaben sind. Ein Eingangs-Repo darf privat sein, auch das eigene Repo ist erlaubt (Standard-Token).
- **Entscheidung (Kern-Schreiber als geschlossene Liste):** `melden.mjs` (Agentenweg für Harness-Befund-Zeilen), `harness-doctor-melden.mjs` und `spezifikation.mjs gescheitert`; ein Wächter in `test/meldung-lib.test.ts` verlangt `bereiteMeldung` für jedes Skript mit `postZeilen(`. Sicherheits-Inboxen und Ticket-Schreiber bleiben draußen (eigenes Folge-Ticket), weil sie Tickets statt Befund-Zeilen anlegen.
- **Entscheidung (Stand als Fußzeile):** eine Zeile je Kommentar (`factory: <Tag> (<Commit>)`), nicht je Zeile; ohne Sync-Stand keine Zeile (das Repo ist selbst Fabrik), ein unlesbarer Stand (kein JSON-Objekt) sperrt das Senden (Exit 1 mit Fix-Zeile, Entscheidung nach der Abnahme von factory#153); ein Lesefehler auf Dateiebene zählt weiter als fehlender Stand.
- **Entscheidung (Sperrprüfung fail-closed):** `check-internalrefs --text` als Kindprozess; nur Exit 0 sendet, jeder andere Ausgang sperrt. Grund: ein stiller Rückfall auf „senden“ würde die Sperrliste umgehen.
- **Entscheidung (Token):** ein eigenes Secret `MELDESTELLE_TOKEN` mit Rückfall auf `PROJECT_TOKEN`, weil das Eingangs-Repo ein anderes Besitzerkonto haben kann als das Factory-Board und das Recht dort nur Issues sein soll. Ein Secret anlegen bleibt Pre-Flight des Beziehers.
- **Grenzen:** Meldetexte fremder Bezieher sind Fremdtext und werden nie automatisch umgesetzt (Nachtrag factory#162, ADR 0031 Punkt 3); der Dedupe des Doctors erkennt an einer fremden Meldestelle die eigenen Zeilen eines fremden Accounts nicht (`istVertraut` prüft gegen den Besitzer); `check-internalrefs --text` prüft keine lokalen Pfade (beides überholt durch Nachtrag factory#208 unten).

## Nachtrag factory#208 (2026-11-05): Sicherheits-Inboxen im Bezieher

- **Entscheidung (Ziel = eigenes Repo):** im Bezieher (Sync-Stand vorhanden) schreiben `audit-einordnung`, `codescanning-inbox`, `secret-inbox` ins eigene Repo statt ins öffentliche Eingangs-Repo der Fabrik; die Fabrik bleibt unverändert. Grund: ein Sicherheitsfund darf das Bezieher-Repo nicht verlassen, der Weg der Harness-Befunde (Meldestelle) ist dafür der falsche (Sicherheitsbefunde gehen über das Private Vulnerability Reporting).
- **Entscheidung (Rest-Zeilen):** die Zeilen ohne eigenes Ticket gehen in `Sicherheit: Rest-Befunde (gesammelt)` im eigenen Repo, ohne 🔒, ans Ende der Todo-Spalte; sie gehören nicht auf die Board-Spitze, weil sie keine Notfälle sind.
- **Entscheidung (Sperrprüfung):** `audit-einordnung` und `codescanning-inbox` rufen `bereiteMeldung` vor `postZeilen`; die Ausnahmeliste des Wächters in `test/meldung-lib.test.ts` entfällt. `wiedervorlage` prüft bei fremdem Ziel-Repo vor dem Anlegen. `check-internalrefs --text` prüft zusätzlich die Pfadregel (alle drei Regeln, Laufwerkspfade auch außerhalb von `test/` und `scripts/`).

## Nachtrag #78: Zählung über beide Repos, weitere Schreibwege

- **Entscheidung (Quote und Takt zählen beide Repos):** führen Produkt- und Factory-Board verschiedene Repos, lesen Takt, Selbst-Audit und Quotenzeile die Commits von `main` beider Repos und stufen jeden Commit nach der Rolle seines Repos ein (Commit aus dem Repo des Factory-Boards ist ein Factory-Merge, aus dem des Produkt-Boards ein Produkt-Merge), weil Ticketnummern nur je Repo eindeutig sind und die Nummernregel sonst falsch zählt. Ein nicht lesbares Repo bricht den Takt ab und steht im Audit als Lücke mit Grund (fail-closed, nie eine Teilmenge). Führen beide Boards dasselbe Repo, gilt weiter die Nummernregel. Das Lesen des Produkt-Repos braucht `PROJECT_TOKEN` mit Lesezugriff.
- **Weitere Ziel-Repo-Wege:** Wiedervorlage legt Tickets im Ziel-Repo an (die Duplikat-Prüfung liest Ziel- und eigenes Repo), Harness-Doctor-Melden und `spezifikation gescheitert` posten im Ziel-Repo; ein fremdes Ziel-Repo nimmt `PROJECT_TOKEN` (`tokenFuerZiel`), das eigene den Standard-Token.

## Nachtrag #97: Token an jedem Ziel-Repo-Aufruf, Repo als Pflicht, kein Rückfall aufs eigene Repo

Verknüpft [Nachtrag #78](#nachtrag-78-zählung-über-beide-repos-weitere-schreibwege); der Nachtrag stellt nichts davon um.

- **Token und Schreibweise:** `spezifikation anlegen` und `sammelticket-anlegen` reichen den Token (`tokenFuerZiel`) an jeden `gh`-Aufruf gegen das Ziel-Repo; das eigene Repo gilt auch in anderer Schreibweise (Groß-/Kleinschreibung) als eigenes und nimmt den Standard-Token. `board-place` setzt den Token einmal beim Start aus dem Ziel-Repo (`--repo`), `spezifikation anlegen` startet es als Kindprozess und reicht die Umgebung weiter.
- **Repo ist Pflicht:** `loadOpenIssuePages` und `itemsUeberIssues` (auch im Takt) verlangen das Repo ausdrücklich, kein stiller Standard; ein Lesefehler im Takt wird über `schreibrechtText` eine Meldung mit Weg zur Abhilfe.
- **Entscheidung (`quelle.repo` ohne Rückfall):** das Factory-Repo des Update-Checks und der Seiten-Links kommt aus `quelle.repo` im Sync-Stand, sonst aus einem ausdrücklich gesetzten `boards[factory].repo`, nie vom eigenen Repo; sonst „nicht bestimmbar“, weil ein Rückfall auf das eigene Repo auf ein Fremdprojekt den falschen Upstream zeigte.
- **Entscheidung (`seitenliterale`):** Fachdomänen-Wörter für den Factory-Seiten-Wächter stehen in der Projekt-Config (`seitenliterale`), nicht als feste Liste im Wächter, weil der Kern kein Projektwort tragen darf.
- **Entscheidung (`struktur.moduldoku: null`):** ein Projekt ohne Modul-Tiefendocs schaltet `check:docmap` damit ab (Exit 0 mit Hinweis); `""` bleibt ein Fehler, damit ein Tippfehler nicht still das Gate abschaltet.
